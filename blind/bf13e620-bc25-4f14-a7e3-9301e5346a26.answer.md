It's decided during argument parsing, before the callback ever gets a chance to run. All references are in `src/click/core.py` unless noted.

1. **The default is set in `Group.__init__` (lines 1785–1789).** If you don't pass `no_args_is_help`, it is set to `not invoke_without_command`. A plain `@click.group()` has `invoke_without_command=False`, so it ends up with `no_args_is_help=True`.
2. **The decision is made in `Group.parse_args` (lines 2038–2040).** If there are no args, `no_args_is_help` is true and `ctx.resilient_parsing` is off (it's on during shell completion), it raises `NoArgsIsHelpError(ctx)`. `Command.parse_args` (lines 1396–1398) has the same check for plain commands, where the default is `False`.
3. **It happens before the callback.** `Command.main` (line 1591) calls `make_context`, which calls `parse_args` (line 1393). So the exception fires before `self.invoke(ctx)` on line 1592, and the callback never runs.
4. **The help text comes from the exception.** In `src/click/exceptions.py`, `NoArgsIsHelpError.__init__` (around lines 332–336) uses `ctx.get_help()` as its message. It is a subclass of `UsageError`, so the exit code is 2.
5. **`main` displays it.** `Command.main` catches it as a `ClickException` (lines 1629–1633) and calls `e.show()`, which prints the help to stderr without the usual "Error:" prefix. In non-standalone mode the exception is re-raised instead.
6. **How the two flags combine.** If `invoke_without_command=True` (so `no_args_is_help` defaults to `False`), parsing succeeds. Then `Group.invoke` (lines 2058–2063) sees there's no subcommand and runs the group's callback through `super().invoke`.
7. **If both are false** (passed explicitly), `Group.invoke` calls `ctx.fail("Missing command.")` (line 2064) and you get a usage error instead of help.
8. **If both are true** (passed explicitly), `no_args_is_help` wins, because `parse_args` runs before `invoke`. You get help even though the callback is allowed to run without a subcommand.
