The decision point is the clock handler `GrooveBox::processClockInput` (`src/modules/GrooveBox/GrooveBox.hpp:1126`). On each rising edge at `STEP_INPUT`, it runs `fireStep()` if `clock_counter == clock_division`; on every other pulse it runs `processRatchets()`.

1. **Step path:** `fireStep` (1142) calls `advanceTracks` (1154), which calls `Track::step()` (`Track.hpp:83`) to move `playback_position` forward and set `ratchet_counter` to 0. The first clock skips the advance. Then `triggerTracks` (1174) calls `GrooveBox::trigger(i)` for each track (450), which calls `Track::trigger()` (`Track.hpp:91`).
2. **`Track::trigger` does:** a probability roll that sets `m.skipped`, then a check that the step is on (`m.steps[...]`). If both pass, it copies that step's parameter locks into `m.local_parameter_lock_settings`, applies sample-start snap, opens the ADSR gate, and calls `sample_player->trigger` (144).
3. **Ratchet path:** `processRatchets` (1184) calls `Track::ratchety()` (`Track.hpp:160`). It fires only if the current step is on and the last step was not skipped (`!m.skipped`). It then looks up `ratchet_patterns[RATCHET lock][m.ratchet_counter]`, and if that slot is set it re-triggers the sample and the ADSR. The counter wraps at 8.
4. **What makes a step sample different from a ratchet sample:**
   - Only the step path advances the position, rolls probability, and reloads the step's parameter locks.
   - A ratchet rolls no probability. It inherits the step's outcome through `m.skipped` and reuses the locks the step already loaded.
   - A ratchet plays only where the per-pulse pattern has a hit.
   - Sample start differs: `trigger` passes the local `sample_start`, read before snapping (`Track.hpp:128`, `144`). `ratchety` reads the snapped value back from the local settings (170). So with snap on, ratchets can start at a different position than the main hit. This looks like a bug.
5. **Mute and solo:** both paths go through `GrooveBox::notMuted` (458). If any track is soloed, only soloed tracks play; otherwise a track plays unless it is muted. The check sits in `GrooveBox::trigger` (453) for steps and inside the `processRatchets` loop (1188) for ratchets.
   - A muted track still advances (`advanceTracks` has no mute check), but its `Track::trigger` never runs. So `m.skipped` and the locks are left over from earlier steps.
   - In the ratchet path, a muted track's `track_triggers[i]` and `ratchet_counter` are not updated at all.
6. **Where mute/solo state comes from:** `processOutputStage` (~1314–1368) copies `mutes`/`solos` from the expander message. A track that gets muted or un-soloed while playing calls `Track::fadeOut()`; `Track::process` stops the player when the fade ends (~362–368).
   - `any_track_soloed` is computed from the *previous* `solos` before the new values are copied in (1317–1327), so solo changes reach `notMuted` one message late.
