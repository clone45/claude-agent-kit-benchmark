GrooveBox has a single clock input. `GrooveBox::processClockInput` (`GrooveBox.hpp:1118–1132`) counts its rising edges with `clock_counter`. When the count reaches `clock_division` (8), the edge is a **step** (`fireStep`); every other edge is a **ratchet tick** (`processRatchets`).

**Step path**
1. **`GrooveBox::fireStep`** (1134–1164): calls `Track::step()` on every track, muted or not, except on the very first step. `Track::step` (`Track.hpp:83`) advances `playback_position` within the track's range and resets `ratchet_counter` to 0. `fireStep` then calls `GrooveBox::trigger(i)` for each track and resets `clock_counter` to 0.
2. **`GrooveBox::trigger`** (450–456): this is where mute and solo enter. It calls `Track::trigger` only if `notMuted(track_id)` (458–463) is true. `notMuted` returns `solos[id]` when any track is soloed, otherwise `!mutes[id]`.
3. **`Track::trigger`** (`Track.hpp:91–150`): this decides whether the track fires. A probability roll comes first; a miss sets `m.skipped = true`. Then the step must be on (`m.steps[playback_position]`). If both pass, it copies that step's parameter locks into `m.local_parameter_lock_settings`, applies snap to the sample start, opens the ADSR gate and calls `sample_player->trigger`.

**Ratchet path**
4. **`GrooveBox::processRatchets`** (1167–1174): calls `Track::ratchety()` only for tracks where `notMuted(i)` is true. A muted track's `ratchet_counter` doesn't advance, and its `track_triggers[i]` keeps whatever value it had.
5. **`Track::ratchety`** (`Track.hpp:160–183`): fires only if the step is on **and** `m.skipped == false`, so a step that lost its probability roll gets no ratchets. It picks a pattern from the step's `RATCHET` lock, and if that pattern's bit at `ratchet_counter` (0–7) is set, it re-triggers the sample and the ADSR.

**How a step sample differs from a ratchet sample**
- A step sample is gated by the probability roll and loads that step's parameter locks.
- A ratchet sample rolls no dice and reads no locks. It reuses the locks captured at the step and depends on the step's outcome through `m.skipped`.
- Odd detail: `Track::trigger` passes the local `sample_start` captured *before* snapping (line 144), while `ratchety` reads the stored value, which *is* snapped. So with snap on, ratchets can start from a different position than the step hit.

**Mute and solo outside the trigger paths**
- The expander message handler (`GrooveBox.hpp`, about 1310–1346) fades out samples that are already playing when a track becomes muted, or un-soloed while another track is soloed (`Track::fadeOut`; the fade is processed in `Track::getStereoOutput`, about 355–367). It then stores `mutes[i]` and `solos[i]` for `notMuted` to use.
