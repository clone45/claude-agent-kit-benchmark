Steps and ratchets are both driven from the clock block in `GrooveBox::process()` (`GrooveBox.hpp:1085-1128`). It counts pulses on `STEP_INPUT`, which is a ×32 clock, against `clock_division = 8`.

1. **Step path, one pulse in 8** (`clock_counter == clock_division`, lines 1087-1117): every track's `Track::step()` runs first (`Track.hpp:83`). It advances `playback_position` and resets `ratchet_counter = 0`. Then each track goes through `GrooveBox::trigger(track_id)` (`GrooveBox.hpp:450-456`), which calls `Track::trigger()` (`Track.hpp:91-150`).
2. `Track::trigger()` makes the decision. It rolls the PROBABILITY lock and stores the result in `m.skipped`. If the roll passes and `m.steps[playback_position]` is on, it copies that step's parameter locks into `m.local_parameter_lock_settings`, applies sample-start snap, then calls `adsr.gate(true)` and `sample_player->trigger(...)`.
3. **Ratchet path, the other 7 pulses** (`else` branch, `GrooveBox.hpp:1118-1126`): it calls `Track::ratchety()` (`Track.hpp:160-183`). That re-fires only if the current step is on and `m.skipped == false`. It then looks up `ratchet_patterns[RATCHET lock][m.ratchet_counter]` and advances the counter (wraps at 8; in practice it only reaches 0-6 before `step()` resets it).
4. **What makes a ratchet different from a step:**
   - A ratchet doesn't evaluate the step: no probability roll, no reload of the parameter locks, no snap. It reuses the `local_parameter_lock_settings` and `m.skipped` left by the last `trigger()`.
   - Which pulses fire comes from the RATCHET pattern indexed by `ratchet_counter`.
   - It calls `adsr.gate(true)` and `sample_player->trigger()` with the stored (already snapped) SAMPLE_START. `trigger()` itself passes the local `sample_start` it read before snapping.
   - Both paths write `track_triggers[i]`, which is sent to the expander at line 1325.
5. **Mute and solo:** both paths are gated by the same check, `GrooveBox::notMuted()` (`GrooveBox.hpp:458-463`). When any track is soloed it returns `solos[i]`, otherwise `!mutes[i]`. The step path checks it inside `GrooveBox::trigger()` (line 453), before `Track::trigger()` runs. The ratchet path checks it inline at line 1123, before `ratchety()`.
6. `Track` itself knows nothing about mute or solo. The flags come from the expander message in `process()` (`GrooveBox.hpp:1242-1295`), which also calls `Track::fadeOut()` on tracks that are still playing and become muted or un-soloed.
7. One side effect: a muted track never runs `trigger()`, so its `m.skipped` and parameter locks stay stale. After unmuting, ratchets can use that stale state until the next step.
