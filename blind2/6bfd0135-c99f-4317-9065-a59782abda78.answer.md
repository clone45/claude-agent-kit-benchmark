**Dispatch:** `GrooveBox.hpp` `process()`, lines 1085–1128. On a STEP_INPUT rising edge, if `clock_counter == clock_division` it is a real step. Otherwise the pulse falls between steps and is used for ratchets.

**Step path:** every track calls `Track::step()` (`Track.hpp:83`), which advances `playback_position` and zeroes `ratchet_counter`. Then `GrooveBox::trigger(i)` (`GrooveBox.hpp:450`) runs and its result goes into `track_triggers[i]`. The fire decision is made in `Track::trigger()` (`Track.hpp:91–150`):
- It resets `fade_out` and rolls PROBABILITY. A failed roll sets `m.skipped = true`.
- If the roll passes and `m.steps[playback_position]` is on, it copies that step's parameter locks into `m.local_parameter_lock_settings` and quantizes SAMPLE_START when snap is set.
- It then gates the ADSR, calls `sample_player->trigger()` and returns true.

**Ratchet path:** for each track, `Track::ratchety()` (`Track.hpp:160–183`) runs and its result goes into `track_triggers[i]`. It fires only if the current step is on and `m.skipped == false`, so it inherits the step's probability result. It looks up `ratchet_patterns[RATCHET][ratchet_counter]` and, on a hit, re-triggers the sample and ADSR. It advances the counter modulo 8.

**Step vs. ratchet sample:**
- A step sample makes the decisions: it rolls probability, loads that step's parameter locks, applies snap and resets the fade-out.
- A ratchet sample makes none of these. It reuses the stored settings and `m.skipped`, and is gated by the ratchet pattern instead of probability.
- One quirk: the step trigger passes the local `sample_start` captured before snapping (`Track.hpp:144`). `ratchety()` reads the stored, snapped SAMPLE_START (`Track.hpp:170`), so with snap on the two can start at different positions.

**Mute/solo:** both paths check `notMuted()` (`GrooveBox.hpp:458`): when anything is soloed only soloed tracks pass, otherwise unmuted tracks pass.
- The step path checks it inside `GrooveBox::trigger()` (line 453), so a muted track's `Track::trigger()` never runs.
- The ratchet path checks it at line 1123. A muted track's `track_triggers[i]` is then left unchanged rather than set to false.
- The `mutes`/`solos` values come from the expander message (`GrooveBox.hpp:1265–1295`). That code also fades out a track that is already playing when it becomes muted or loses out to a solo, by calling `Track::fadeOut()`.
