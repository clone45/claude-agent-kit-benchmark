The step path and the ratchet path split in `GrooveBox::process`, `src/modules/GrooveBox/GrooveBox.hpp:1085-1128`. Each pulse on `STEP_INPUT` bumps `clock_counter`. When it equals `clock_division` (8), the pulse is a step; on the other 7 pulses it is a ratchet tick. `clock_counter = clock_division` at 1036 makes the next pulse a step.

**Step path** (GrooveBox.hpp:1087-1117):
- Every track first calls `Track::step()` (`Track.hpp:83-89`), except on the very first pulse. That moves `playback_position` forward, wrapping within `range_start..range_end`, and sets `ratchet_counter` back to 0.
- Then `GrooveBox::trigger(i)` (GrooveBox.hpp:450-456) runs. **Mute/solo enter here**: it calls `Track::trigger()` only if `notMuted(i)` is true.
- `Track::trigger()` (`Track.hpp:91-150`) makes the actual decision. It clears any fade-out, then rolls `PROBABILITY` (it always fires when the value is ≥ 0.98) and records `m.skipped`. If the step is on (`m.steps[playback_position]`), it copies that step's parameter locks into `m.local_parameter_lock_settings`, snaps `SAMPLE_START` to the grid, sets the ADSR gate and triggers the sample.

**Ratchet path** (GrooveBox.hpp:1118-1126):
- **Mute/solo enter here** as an inline `if (notMuted(i))` check before `Track::ratchety()` (`Track.hpp:160-183`).
- `ratchety()` fires only if the current step is on and `m.skipped` is false, so a step lost to the probability roll gets no ratchets. It picks a pattern from the `RATCHET` lock (167) and indexes it by `ratchet_counter`, which wraps at 8. When the pattern bit is set it re-triggers the sample and the ADSR.

**How a ratchet differs from a step sample:** a ratchet does no probability roll and no fade reset, and it never re-reads the step's locks; it reuses the ones `trigger()` cached in `local_parameter_lock_settings`. One quirk: the step trigger plays `sample_start` from before the snap (`Track.hpp:128` → 144), while ratchets play the snapped value (170).

**Where mute/solo come from:** `notMuted` (GrooveBox.hpp:458-463) returns `solos[i]` when `any_track_soloed` is set, and `!mutes[i]` otherwise. The expander fills those arrays (1244-1253, 1294-1295) and fades out tracks that are already playing (1280-1290). Without the expander, everything is cleared (1336-1341).

When a track is muted, the ratchet path leaves `track_triggers[i]` untouched, so the expander keeps seeing the step's last value. The step path writes `false` instead.
