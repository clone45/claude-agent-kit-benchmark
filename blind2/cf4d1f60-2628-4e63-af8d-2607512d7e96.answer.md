Both paths start in `GrooveBox::process`, in `GrooveBox.hpp`, on each rising edge of STEP_INPUT (line 1085). Which path runs depends on `clock_counter` compared with `clock_division`.

- **Step path (`clock_counter == clock_division`, lines 1087–1114):** each track advances with `Track::step()` (`Track.hpp:83`), which moves `playback_position` and resets `ratchet_counter` to 0. Then `GrooveBox::trigger(i)` (`GrooveBox.hpp:450`) calls `Track::trigger(snap)` (`Track.hpp:91`). That function makes the fire-or-not decision: it rolls PROBABILITY, setting `m.skipped` if the roll fails. Otherwise, if `m.steps[playback_position]` is on, it copies that step's parameter locks into `local_parameter_lock_settings`, quantizes SAMPLE_START when snap is on, gates the ADSR and calls `sample_player->trigger`.
- **Ratchet path (the other clock edges, the `else` at lines 1118–1126):** `Track::ratchety()` (`Track.hpp:160`) fires only if the current step is on and `m.skipped == false`. It chooses a pattern from the RATCHET lock, checks `ratchet_patterns[pattern][ratchet_counter]` and, on a hit, re-triggers the sample and ADSR. The counter wraps after 8.
- **What makes them different:** a step sample is the only one that rolls probability, reloads parameter locks from the step, applies snap, and resets the fade-out (`fade_out.reset()`). A ratchet sample does none of that. It reuses the lock values and the `m.skipped` result left by the last step trigger, and it is gated by the ratchet pattern and counter.
- **One quirk:** a step trigger passes the local `sample_start`, which is the value before snapping (`Track.hpp:122,144`). A ratchet passes the stored lock value, which is the snapped one (`Track.hpp:170`). So with snap on, the ratchets can start from a different position than the step hit they follow.
- **Mute and solo:** both paths use the same gate, `GrooveBox::notMuted()` (`GrooveBox.hpp:458`). If any track is soloed it returns `solos[i]`, otherwise `!mutes[i]`. The step path checks it inside `GrooveBox::trigger` (line 453), so a silenced track never reaches `Track::trigger` and its probability, skip flag and locks are not updated. The ratchet path checks it inline before `ratchety()` (line 1123), so `ratchet_counter` doesn't advance and `track_triggers[i]` isn't rewritten. That value then stays at whatever the step path last set, which while muted is `false`.
- **Where mute and solo come from:** `mutes`, `solos` and `any_track_soloed` are filled from the expander message in `process` (`GrooveBox.hpp:1243–1295`). That same block fades out tracks that are already playing when they become muted or un-soloed. `any_track_soloed` is computed from the previous `solos` values before the new ones are copied in, so a solo change takes effect one expander message late.
