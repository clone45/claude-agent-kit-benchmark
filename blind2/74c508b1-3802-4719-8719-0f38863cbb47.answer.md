Both paths start in `GrooveBox::process`, in the clock block at `GrooveBox.hpp:1085–1128`. Each STEP_INPUT pulse goes to one path or the other depending on `clock_counter` against `clock_division` (8).

1. **Step path** (`GrooveBox.hpp:1087–1117`, runs when `clock_counter == clock_division`): every track calls `Track::step()` (`Track.hpp:83`), which moves the playhead forward and resets `ratchet_counter` to 0. Then `GrooveBox::trigger(i)` (`GrooveBox.hpp:450`) runs for each track.
2. **Step: the fire decision** is in `Track::trigger()` (`Track.hpp:91–151`). It rolls the PROBABILITY lock and records the outcome in `m.skipped`. If the roll passes and `m.steps[playback_position]` is set, it copies that step's parameter locks into `m.local_parameter_lock_settings`, snaps SAMPLE_START if snap is on, gates the ADSR and calls `sample_player->trigger()`.
3. **Ratchet path** (`GrooveBox.hpp:1118–1126`, the `else` branch): runs on the other 7 of every 8 pulses and calls `Track::ratchety()` (`Track.hpp:160–183`). It re-fires only if the current step is on, `m.skipped == false`, and the RATCHET pattern bit at `ratchet_counter` is set. The counter wraps at 8, but only indices 0–6 are reached between steps.
4. **What distinguishes them:** a step sample makes a fresh probability roll and loads that step's parameter locks. A ratchet sample makes no roll of its own: it inherits the step's outcome through `m.skipped` and reuses the locks already loaded. Only the step path calls `fade_out.reset()`. The step path also passes the pre-snap `sample_start` local (`Track.hpp:144`), while a ratchet passes the snapped value from the stored locks (`Track.hpp:170`), so with snap on the two can start at different positions.
5. **Mute and solo** are both decided by `GrooveBox::notMuted()` (`GrooveBox.hpp:458`): if any track is soloed, only soloed tracks pass; otherwise a track passes when it isn't muted.
   - In the step path the check is inside the `GrooveBox::trigger()` wrapper (`:453`), so a muted track never calls `Track::trigger()` and its `m.skipped` and locks keep their old values.
   - In the ratchet path the check is inline at `:1123`. A muted track's `track_triggers[i]` isn't updated, so it keeps its last value.
6. **Where mute and solo are set:** the expander message handler (`GrooveBox.hpp:1244–1295`) fills `mutes`, `solos` and `any_track_soloed`. When a track newly becomes muted or loses out to a solo, it calls `fadeOut()` to cut a sample that is already playing.

**Possible bug:** if a track is unmuted partway through a step, its next ratchet pulses check only the old `m.skipped` and locks from the last step it actually played. They may fire using that stale state.
