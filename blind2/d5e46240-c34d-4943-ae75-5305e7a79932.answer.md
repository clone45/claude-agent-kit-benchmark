A step trigger and a ratchet are decided in two separate branches of the same clock-input handler in `GrooveBox::process`. Mute and solo are checked separately on each path, through the same helper.

1. **Clock divider:** `GrooveBox::process` (`src/modules/GrooveBox/GrooveBox.hpp:1085`) watches the clock input with `step_trigger`, which is meant to run at 32 pulses per step. When `clock_counter == clock_division` (8, line 55), the pulse is a real step (lines 1087–1117). Every other pulse goes to the ratchet branch (lines 1118–1126).
2. **Step path:** each track first advances with `Track::step()` (`src/modules/GrooveBox/Track.hpp:83`). This moves `playback_position` forward, wrapping within the track's range, and resets `ratchet_counter`. The very first step after start is not advanced. Then `GrooveBox::trigger(i)` (`GrooveBox.hpp:450`) calls `Track::trigger()` (`Track.hpp:91`).
3. **`Track::trigger`:** it rolls the per-step `PROBABILITY` lock and stores the result in `m.skipped`. If the step is on (`m.steps[pos]`), it copies all of that step's parameter locks into `m.local_parameter_lock_settings`, quantizes the sample start to the snap value, gates the ADSR, and calls `sample_player->trigger`.
4. **Ratchet path:** `Track::ratchety()` (`Track.hpp:160`) fires only if the current step is on and was not skipped by probability. It picks a pattern from the `RATCHET` lock (`ratchet_patterns` in `src/modules/GrooveBox/defines.h:138`, 16 patterns × 7 slots) and indexes it with `ratchet_counter`, which advances on every off-step pulse. Each slot that is true re-triggers the sample and the ADSR.
5. **How a ratchet differs from a step:** a ratchet does no probability roll, doesn't reset the fade-out and doesn't reload parameter locks. It replays whatever `Track::trigger` last stored in the local settings.
   - **Possible bug:** the step path passes the pre-quantized local `sample_start` (`Track.hpp:126, 144`), while ratchets read the snapped `SAMPLE_START` from the local settings (line 170). With snap on, a ratchet can start at a different point than its step did.
6. **Mute/solo on the step path:** `GrooveBox::trigger` checks `notMuted(track_id)` (`GrooveBox.hpp:458`) before calling `Track::trigger`. If any track is soloed, only soloed tracks play; otherwise any track that isn't muted plays.
7. **Mute/solo on the ratchet path:** the same `notMuted(i)` check sits at the call site (`GrooveBox.hpp:1123`). A muted track's `Track::trigger` is never called, so `m.skipped` and its local locks keep their values from before the mute.
8. **Where mute/solo come from:** the `mutes`/`solos` arrays and `any_track_soloed` are filled from the expander message (`GrooveBox.hpp:1244–1295`). That code also calls `Track::fadeOut()` on a track that is still playing when it becomes muted or un-soloed. Both paths store their result in `track_triggers[i]`, which is sent to the expander (lines 1325–1327).
