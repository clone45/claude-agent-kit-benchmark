How We Tested Agent Kit

A short account of how we measured claude-agent-kit against a plain Claude Code session, written so the plugin's authors can see exactly what we did, judge whether it was fair, and repeat it.

Why we measured

The plugin makes a clear claim: cheaper models can do the reading, searching, and routine implementation through subagents, so the main Opus session keeps its context small and spends its tokens on judgment and review. That is a testable claim, and the README publishes no measurements. We wanted numbers rather than impressions, for the four things a user would care about: cost per task, quality of the result, time taken, and how much context the main session ends up carrying.

Two conditions, one difference

A: plain session
  • Claude Code 2.1.303, run headlessly with claude -p
  • Opus 5.5 as the main model, effort high
  • A short CLAUDE.md with the project's test and check commands
  • No plugin, no other user-level plugins or MCP servers
B: the same session with the plugin
  • Everything in A, unchanged
  • The plugin at commit c8dfca7 loaded for the session with --plugin-dir
  • Its "Agent contract" section appended to the same CLAUDE.md, filled in from the template with the project's real commands
  • Its hooks live: the orchestration rules injected at session start, the read-budget hook on Read and Bash

Both conditions started every task from the same commit with the same prompt, in bypass-permissions mode so nothing waited on a human, with user-level settings excluded so that only the plugin distinguished them. The repository was reset before every run and the auto-memory folder cleared, so runs could not learn from each other. The two conditions were interleaved in random order.

The tasks

We used two codebases and chose tasks whose outcome a script could judge.

  • pallets/click, a Python library of about 13,000 lines with a six-second test suite: 17 tasks, each in a fresh session. Six bug fixes and two small features were built by reverting real upstream commits and holding their tests back as hidden tests; three refactors; four "find where this happens" questions with an answer key; two longer multi-step tasks.
  • Voxglitch, a VCV Rack plugin of about 73,000 lines of C++ with 54 files over the plugin's 350-line threshold: 8 tasks, all new work the codebase had never seen, including three questions that require reading the largest headers, two engine features with hidden tests we wrote, one seeded regression, one refactor of a 400-line method, and one feature that spans engine, panel widget, and manual.

Each task's starting tree is a single squashed commit with the changelog removed, so there is no history to mine for the answer. The Voxglitch tasks were also run as one continued session, task after task, with the harness committing a checkpoint after each so that context accumulates the way it does in a working day while every task is still diffed and checked on its own.

What we counted, and how

  • Tokens come from Claude Code's own records: the per-model usage in each run's final result, which includes subagent requests, plus the per-call stream for cache-tier and context-size detail. Subagent transcripts give the model and call count of every delegated agent.
  • Cost is those tokens priced at Anthropic's published per-token prices on the day, including cache writes and cache reads, per model. The runs used a Max subscription, so nothing was billed; the figures say what the same work would cost through the API. Our arithmetic matches Claude Code's own cost estimate to the cent.
  • Quality is automatic where it can be: hidden tests, the project's full suite or standalone tests, lint and type checks or a syntax-only compile against the Rack SDK headers. Find-where answers are graded against an answer key, and every diff is also saved under a random id for grading without knowing the condition.
  • Time is wall-clock around the whole run. Context is the prompt size of the main session's last API call, against the 1,000,000-token window Opus 5.5 has in Claude Code, plus any compaction events in the transcript.
  • Plugin activity is counted directly: subagent calls by agent type, reads the hook denied, and review rejections that sent work back.

Each task runs three times per condition on click and twice per condition and session shape on Voxglitch, because model output varies from run to run. We report the spread, and we say so when a difference between conditions is smaller than that spread.

Two things we changed, disclosed

  • The plugin's SessionStart hook matches startup|resume|clear|compact. Claude Code reports a session started with --fork-session as fork, so in our copy we added fork to that matcher. It has no effect on any run that starts fresh or resumes.
  • One Voxglitch task is a seeded regression: we removed one line from the Euclid engine so that a reset no longer arms its clock-ignore window, and described the symptom the way a user would. The engine's own tests, held back as hidden tests, detect it. Every other task is either a real upstream change or new work.

Where this test is limited

  • It is headless. Nobody answers questions mid-task, so a session that stops to ask is counted as it ended. The plugin was designed with a person in the loop.
  • Most tasks finish in a few minutes. Only the chained Voxglitch sessions let context accumulate, and even those stay far from the 1M window, so compaction never happens.
  • Opus 5.5 has a 1M window and inexpensive cache reads. Claims written for 200K windows and five-minute caches may hold better there than here.
  • A subscription gets one-hour cache writes; API users get five-minute writes at a different price and more cache misses, so the exact dollar figures will not transfer.
  • Quality is near its ceiling on these tasks, so a review gate has little room to show a benefit. Two or three repetitions also leave small real differences inside the spread.
  • Both repositories are far smaller than the monorepos where reading costs dominate.

If the authors consider some other setup the fair one, for instance a particular Agent contract, a different main model, or a task shape the plugin is meant for, the harness can run it: every task, prompt, and command is a file, and a run is one command.

Repeating it

python3 make_tasks.py --rebuild --verify     # click: build task trees, confirm hidden tests fail before the fix
python3 run.py --reps 3                     # run every task in both conditions, reset between runs
python3 make_tasks2.py --rebuild --verify    # voxglitch: the same, plus chain bases
python3 run2.py --config config2.json --modes fresh,chain --reps 2
python3 summarize.py --config config.json    # tables with means and spread, per task type
python3 report.py --config config.json --config config2.json

The harness is a folder of plain Python scripts, task prompts, hidden tests, answer keys, and a price table, with every run's raw output, transcript, diff, and check results saved alongside. The results themselves are on a companion page.
